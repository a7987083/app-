1. 卡密授权查询 POST /authorization HTML 页面

用途：查询指定卡密与 UDID 的授权状态。当前实现将查询结果渲染到网页，不返回纯 JSON。

什么时候调用：网页自助查询授权信息时；OC/Swift 客户端不要把它当 JSON API。

参数：code 卡密（必填），udid 当前设备 UDID（必填）。

POST /authorization
code=XXXX-XXXX
udid=000081...

下一步：未激活时调用 /appstore；日常旧授权检查使用 /index/index/apiface，Dylib 保护使用 Secretless v3 Verify。

2. 卡密激活 / 软件源刷新 GET /appstore 程序接口

用途：带 code 时激活一次性卡密并绑定 UDID；不带 code 时刷新软件源。

什么时候调用：首次激活卡密，或已授权设备刷新软件源数据。

参数：udid 必填；code 激活时必填、仅刷新时可省略。

GET /appstore?udid=<UDID>&code=<CARD_CODE>

下一步：激活成功后原 /index/index/apiface 继续可用；首次设备密钥登记使用当前已激活卡密。

3. 已激活设备授权校验 GET /index/index/apiface JSON

用途：保留 2428 原 API：按 UDID 查询已激活且未过期授权，返回 expire / ts / nonce / sign。

参数：udid 必填。

GET /index/index/apiface?udid=<UDID>
4. 旧远程 Dylib 配置 GET /index/index/dylib JSON

用途：保留 2428 原 API，返回旧协议远程 Dylib 配置与当前 UDID 授权状态。

GET /index/index/dylib?udid=<UDID>
5. 设备换绑提交 POST /unbind HTML 页面

用途：保留 2428 换绑页面入口。

参数：code、old_udid、new_udid 均必填。

6. 换绑状态查询 GET /unbind/query JSON

用途：保留 2428 API，查询当前 UDID 有效授权及换绑资格。

GET /unbind/query?udid=<UDID>
7. Dylib Runtime Config GET /index/dylib_verify/config?dylib_key=... 核心

用途：按 Dylib Key 获取 RSA 签名后的运行配置、API Endpoint、Verify Path 和配置版本。

失败：config_unavailable。客户端可使用 Last-Known-Good 配置或已有 endpointURL 兜底。

下一步：使用生成配置中的服务器公钥验签，然后请求 Challenge。

8. Dylib 一次性 Challenge POST /index/dylib_verify/challenge 核心

用途：签发一次性 Challenge，并判断设备 P-256 公钥是否需要首次登记。

{
  "udid":"<UDID>",
  "dylib_key":"<DYLIB_KEY>",
  "device_public_key":"<P-256 SPKI PEM>"
}

下一步：用 Keychain 私钥对 canonical v3 签名；首次登记时 Verify 请求附带当前已激活卡密。

9. Dylib 在线验证 POST {$runtimeConfig.verify_path|htmlentities} 核心

用途：验证一次性 Challenge、设备签名、App 身份、Dylib Key、版本/Build/SHA256，并继续执行原 2428 权限、公告、更新和离线策略。

Content-Type：application/x-www-form-urlencoded 或 application/json。

调用顺序：Runtime Config → RSA 验签 → Challenge → P-256 签名 → POST Verify → 判断 ok + code + action。

客户端不再存在 Verify Secret。 设备使用独立 P-256 Keychain 私钥；服务器 Runtime Config 使用独立 RSA-2048 私钥签名，生成代码仅含服务器公钥。

以下保留原业务错误码，并新增 Challenge/Device Key 认证错误码。未知 code 仍按 action 处理。

code含义客户端建议
ok / ok_testing / ok_deprecated验证通过消费 permissions/token/notice/app_update。
challenge_expired / challenge_replayed / challenge_mismatch一次性 Challenge 无效重新申请 Challenge 并重新签名。
device_signature_invalid / device_key_mismatch设备证明或已登记公钥不匹配检查设备 Key；需要时后台撤销旧 Key 后重新登记。
device_enrollment_denied首次公钥登记未通过现有卡密授权提供当前 UDID 已激活且有效的卡密。
dylib_unknownDylib 不存在或已停用按 action 停止受保护能力并显示 message。
blacklisted设备被封禁按 action 处理并显示 message。
app_identity_incompleteApp 身份字段不完整补齐 executable / Mach-O UUID。
app_identity_unknown / app_identity_unbound / app_identity_ambiguous / app_identity_inactiveApp 身份解析失败检查身份字段或后台解析/绑定数据。
app_not_authorized / license_invalid授权不适用或无效/过期显示 message；实际授权 UI 由客户端负责。
version_unknownDylib 版本未登记检查 version/build 与后台登记是否一致。
version_blocked / version_revoked版本被阻止/撤销按 action 处理并显示版本 notice/message。
integrity_mismatchDylib SHA256 不一致停止受保护能力并检查实际加载文件。
server_error验证服务异常按 action + offline_grace_seconds 处理临时故障。
config_unavailable运行配置暂不可用使用 Last-Known-Good / endpointURL 兜底。
推荐接入顺序
用户输入卡密
  ↓
网页授权查询（可选） /authorization
  ↓
未激活 → /appstore?udid=...&code=...
  ↓
旧授权兼容检查 → /index/index/apiface?udid=...
  ↓
Dylib 启动 → /index/dylib_verify/config?dylib_key=...
  ↓
RSA 公钥验签 Runtime Config
  ↓
POST /index/dylib_verify/challenge
  ↓
设备 P-256 Keychain 私钥签 canonical v3
  ↓
首次设备 Key 登记时附带已激活卡密
  ↓
POST {$runtimeConfig.verify_path|htmlentities}
  ↓
ok → code → action → message / permissions / notice / app_update
  1. 客户端工程自行取得 UDID、BundleID、版本等业务输入。
  2. 页面型入口与 JSON API 分开处理，不要把 HTML 当 JSON。
  3. 每次 Verify 使用新的 Challenge；设备私钥不离开 Keychain。
  4. 先看 ok，再看 code 和 action；message 只用于提示。
  5. 验证成功后，客户端自行决定菜单、弹窗、悬浮窗、公告显示等产品行为。
